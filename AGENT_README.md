# AGENT_README — Automatic Fish Midline Segmentation

> Authoritative technical reference. The user-facing `README.md` is the short overview; keep both in sync when behaviour changes.

Generates **joints** (straight segments) for robotic fish from real or synthetic **fish midlines** (curved body shapes over time). A joint config approximates every frame's curve with one set of segments, bounded by an error threshold.

## Core data model (CRITICAL — two orientations)
- **`core.Midline`**: every generation-format midline is now a `Midline` — a thin, list-compatible wrapper (indexing `midline[p][f]`, `len`, iteration and `np.asarray` behave exactly like the raw list, so algorithms are unchanged) that also exposes the canonical view and padding info: `.frame_major` (cached `(frames, points, 2)` numpy array — the working representation for vectorized metrics), `.render` (lazy `[frame][point][x, y, z]` conversion, zero-padded per frame), `.real_lengths` (per-frame real point counts from the CSV loader), `.num_points`/`.num_frames`/`.shape`.
- **generation format** `midline[p][f][x, y]` — `p` = point/row index along body (0=head … N-1=tail), `f` = frame/time index. Used by all generation methods and error functions. `load_midline_data` (xls), `load_3d_csv_data(..., for_generation=True)` and `load_data_file` return a `Midline`.
- **render format** `midline[f][p][x, y, z]` — used for 3D plotting; returned as plain lists by `load_3d_csv_data(..., for_generation=False)` / `load_3d_render_data`, or via `Midline.render`.
- **joints** `[[x, y, point_index], ...]` — sorted head→tail. `x,y` are taken from frame 0 (`midline[idx][0]`); errors are evaluated across *all* frames using `point_index`.
- Padding: CSV frames with fewer points are padded **per orientation**. The **generation format** repeats each frame's last real point (tail extension — the loader records the real counts in `Midline.real_lengths`), so generation methods and error metrics never evaluate against synthetic zero points. The **render format** is zero-padded; `is_padding_point()` detects it. `midline_segments()`/`trace_all_frames()` skip padding and order points into a nearest-neighbour chain (data can be unordered) for rendering.

## Generation methods (implemented once in `generation_methods.py`)
All take `midline=...` + one param, plus optional `step_callback(joints, midline, step_index)` (used by the CLI step viewer — raise `main.StepViewerStopped` to abort).

The four growth methods are **not duplicated per metric**: they take `metric='area'|'linear'` and score segments via a metric strategy (`METRICS` dict in `generation_methods.py`). The modules `generation_methods_area_error.py` / `generation_methods_linear_error.py` are thin wrappers that fix the metric, so `gm_a.grow_segments(...)` and `gm_l.grow_segments(...)` behave exactly as before. **Adding a new error metric = adding one strategy to `METRICS`.**

**Convention: every method returns a config that spans the whole body head→tail — the tail point is always the final joint** (grow methods append it when the loop ends; `bs_mp` has a no-progress guard that closes at the tail instead of looping forever). `find_total_error`/`per_frame_error` also append the tail internally, so error metrics are unaffected by this.

Linear (`generation_methods_linear_error`, `error_threshold` in cm) & Area (`generation_methods_area_error`, `error_threshold` in cm²):
- `grow_segments` — Otar's incremental method: walk points; when avg error ≥ threshold, place a joint and backtrack one.
- `grow_segments_binary_search` — binary-search farthest point under threshold from current joint.
- `grow_segments_binary_search_midpoint_only` — greedy, samples error at the midpoint only.
- `grow_segments_from_inflection` — joint at max-gradient (inflection) point; backs off until error ok.

Fixed count:
- `create_equal_segments(midline, segment_count)` — places `segment_count` segments = `segment_count+1` joints, evenly spaced head→tail (tail included).
- `create_diminishing_segments(midline, segment_count)` — halves the remaining body each step, saturates at the tail (≤ ~log₂(n) joints, no duplicates).

Area-only brute force (slow, O(joints·error-computes), pass `resolution_division` to subsample):
- `generate_segments_to_quantity(midline, max_number_of_joints)`
- `generate_segments_to_max_area_error(midline, total_area_max)`

## Error metrics (`calculate_error.py`)
- `find_area_error(s, e, f, midline)` — trapezoid area between joint segment and midline (handles vertical segments).
- `find_linear_error(seg_beg, seg_end, point)` — perpendicular distance point→segment.
- `find_total_error(joints, midline)` → `[avg_linear, avg_area]` per frame; `find_per_frame_error(joints, midline)` → `(linear[], area[])` per frame. Both are **vectorized** (numpy, frame-major array via `to_frame_major`), so they are fast on large CSVs, and they are **pure**: they evaluate against a local copy of `joints` (via `joints_with_tail`) and never mutate the caller's list.
- Scalar helpers `find_area_error`/`find_linear_error` stay for the per-frame search loops; vectorized equivalents `area_scores`/`linear_sum_scores`/`linear_max_scores`/`linear_distances` operate on the frame-major array.

## Data loading (`core.py`)
- `.xls`: `load_midline_data(loc)` → generation format. Rows=points, column pairs=frames. Requires `xlrd`.
- `.csv`: `load_3d_csv_data(loc, midline_type='midline'|'raw', for_generation=True|False)` (single implementation; all modules call it via `core`). Auto-detects `Midline_X/Y` (with optional `Midline_Z`) vs `Relative_X/Y` columns, drops NaN; short frames are padded per orientation (see Padding above). `load_data_file` (gen format) / `load_3d_render_data` (render format) dispatch on extension.
- Synthetic: `generate_midline_from_sinewave(cycles, amplitude, length_cm, phase_difference, frames, resolution)` → generation format.

## Web viewer notes
- Requires Flask (installed). Server sets matplotlib `Agg` and caches per-file display data + midlines (`DISPLAY_CACHE`, `MIDLINE_CACHE`) and generation results (`CACHE`), so repeats are fast even for the 598-frame CSVs.
- Config: `FISH_DATA_FOLDER` / `FISH_PORT` env vars override the positional args (useful when embedding the app in tests).
- The browser auto-opens; `webbrowser.open` runs in a daemon thread. Don't launch the server in a foreground shell without a timeout in tests (it blocks forever).
- When testing the frontend headlessly, use Node + a stubbed DOM; make sure `fetch` is rebound to the real node fetch to avoid infinite recursion.

### Frontend architecture (`web/index.html` → `web/js/app.js`, ~1,300 lines)
- `index.html` is markup only and imports `web/js/app.js` (the fluid page imports `web/js/fluid.js`). Both share `web/js/helpers.js` (pure math/export helpers — keep them DOM-free so node can unit-test them) and `web/js/methods.js` (fetches the method list from `/api/methods`; static fallback if the server is unreachable). `METHODS` is refreshed at init before any card is created.
- **Multi-card deck**: `#deck` holds one self-contained `.card` per dataset. Each card = header (title, link icons, meta, master switch, remove) → canvas (`.cv`, 280px, equal-aspect 2D) → `.cardLog` (status under graph) → `.cardControls` (data-source dropdown `.fileSel`, algorithm select, threshold+segments sliders, 2D/3D, ghost/echo, play, frame) → panels: Generation result + vertical error chart (`.row2`, 2 columns) + Segment lengths (`.segTable` scroll-capped with `.segSummary`).
- **Per-card state** lives on each card object in the `cards` array (data, gen, frame, mode, yaw/pitch/zoom, history, cloud, master). All draw functions are card-aware (`cardDraw`, `cardDraw2d`, `cardDraw3d`, `cardDrawErr`, etc.). Pure helpers (`makeMap`, `bounds2d`, `buildCloud`, `setupCanvas`) take data, not card.
- **2D equal aspect**: `makeMap` uses one scale for both axes and centers the plot (`plotL/plotT/plotW/plotH`); grid clipped to that rect.
- **3D**: orbit camera (`yaw` about up, `pitch` tilt) + ground grid + precomputed decimated `cloud` (≤10k pts) + `requestAnimationFrame` throttle on drag (`request3dRedraw`). 3D button auto-disabled when data has no Z.
- **Dark mode**: every page has a `#themeToggle` button that flips `document.documentElement.dataset.theme` (`light`/`dark`) and persists it in `localStorage` under `fishseg-theme`; the default follows `prefers-color-scheme`. A tiny inline `<head>` script in each HTML page applies the saved theme before first paint (no flash). The CSS `:root`/`:root[data-theme="dark"]` variable blocks theme every element (panels, inputs, chips, hovers, chart backgrounds via `--chartBg`), and the canvas drawing code reads `themeColors()` from `helpers.js` at draw time (grid/text/marker colors per theme), so toggling just sets the attribute and calls the page's `redrawAll()` (viewer: all cards + compare; fluid: frame/flow/compare charts without resetting the selected run; steps: `drawAll`).
- **Linking**: each card has 6 link icons (frame, threshold, segments, data source, play, algorithm/method) — inline SVG with `stroke="currentColor"` (emoji would not recolor). `links` maps var → Set of cards. "link all" button ticks/clears all 6. A draggable `#master` window lists only ticked vars (slider + number box for frame/threshold/segments, file dropdown for data, Play/Pause-all button, method dropdown) and `masterApply(var, val)` drives every linked card (skips cards with `master === false`). Per-card `.masterSwitch` (power icon, amber=on/gray=off) blocks master-driven changes. Play link syncs play/pause across cards (`setPlaying`, driven from `togglePlay`). Editing a card's OWN method/threshold/segments controls never propagates — linked membership only means the master window can drive that card (the algorithm link is driven via the master window's method dropdown, which also clears history + regenerates). Every card also has its own data-source dropdown (`.fileSel`, options synced from the header file list on folder load) so each container's data can be changed independently, and a "sim" button that opens the fluid page prefilled with that container's file/method/param.
- **Hover tooltips**: every slider, button and the key selects across the three pages carry a `title` attribute with a short description of the function/variable (including the dynamically-created card controls in `app.js`'s `cardTemplate`). No JS needed - native browser hover tooltips.
- **Draw robustness**: `cardDraw` clamps `frame` to valid range; `draw2d`/`draw3d` fall back to `[]` for out-of-range traces.
- **Error chart**: per-frame error bars with a metric toggle (`.errMetric` select, area cm² or linear cm); click a bar to jump to that frame.
- **Segment lengths**: table/heatmap toggle in the segment-lengths panel. `cardComputeSegHm` builds `card.segHm` (segments × frames matrix, computed once per generation); heatmap shows length per segment over time (min blue → max red) with a white current-frame marker — reveals how segment chords stretch/shorten during swimming.
- **Exports**: per-card "export" button (`exportCardCsv`) downloads per-frame errors CSV + segment-lengths CSV; "png" button (`exportCardPng`) downloads the plot canvas as PNG; compare panel "Export CSV" (`exportCompareCsv`) downloads the collected comparison history (file, method, param, joints, avg linear, avg area, time). All via `downloadBlob`/`downloadCsv` helpers.
- **Stats**: generation result panel now also shows max linear/area error per frame.
- **Compare panel**: collapsible `#compare` strip under the header ("Compare results") with 4 mini line+scatter charts — avg linear error, avg area error, generation time, joints. One colored series per card (palette by card id), x = parameter (threshold cm² / segment count). Each card keeps a param-keyed generation history (`card.hist`, Map); points accumulate as sliders move and replace in place for repeat params. Legend lists file + method. Hover shows card name, method, param, value. Cleared on method change / data load, via the "Reset curves" button, or exported via "Export CSV". Hover hit-testing uses `cmpLayout(metric, w, h)` with explicit sizes — never resizes the canvas, so hovering can't clear the drawing.
- **Play animation**: `setPlaying` runs a setInterval that moves `card.frame += card.playDir` and bounces at both ends (ping-pong traversal, `playDir` flipped at frame 0 and last frame; reset to 1 on data load). `togglePlay` syncs to linked cards via `links.play`.
- **Sessions**: header "Save session" button POSTs the whole viewer state — data folder, per-card file/method/params/frame/mode/ghost/echo/master switch + compare history, and link membership — to `/api/session/save`, which creates a new `sessions/session_<timestamp>/` folder in the project root (gitignored) with `session.json`. "Load session" (dropdown of `/api/sessions`) restores it: cards are rebuilt with restored settings (created via `createCard` with a `card.loadPromise` that resolves when data+generation finish), links re-applied, frames/modes/history restored. Endpoint `/api/session/load` rejects names with path separators or leading dots.
- Server downsamples frames to ≤240 for the browser (`MAX_FRAMES`); trace indices sent so unordered CSV points draw correctly and joints (row indices) map onto the traced line.

### Fluid simulation page (`/fluid`, `web/fluid.html`)
- Separate page reachable via the "Fluid sim" link in the main viewer header or the per-card "sim" button (opens `/fluid?folder=&file=&method=&param=`, so the page prefills and auto-runs the same configuration). Directory navigation works like the main page (folder input + `#dirs` chips).
- **Two movement modes** (`#simMode`): `tethered` (default — head oscillated in a background current, the original flume test) and `swim` (FREE SWIMMING — the joints are actuated with a traveling wave of joint angles, exactly what a robotic fish's servos do, and the fish propels itself; the flow slider becomes a background-current dial, `amp`/`freq` become the **tail-beat lateral amplitude (cells) and frequency (cycles/step)** of the wave, and a **wave-cycles slider** (0.4–2 cycles along the body) appears). `GET /api/fluid/simulate` accepts `mode`, `cycles` on top of the existing params; in swim mode the response carries `metrics` (speed, speed in body lengths/s, thrust, actuation power, Froude efficiency, cost of transport, Strouhal, measured tail amplitude, wave-tracking RMS, yaw RMS, wake speed, finiteness) and every frame carries the **commanded-wave ghost polyline** (`target`, drawn cyan-dashed in front of the red body) so you can see how well the config executes the commanded wave. The diagnostics panel lists the swim metrics.
- `GET /api/fluid/compare` runs **several generation methods through the SAME free-swim simulation** and returns per-run `metrics`, downsampled time `series` (t, speed, thrust, power, tail_y, flow) and compact `frames` (≤120, incl. target ghosts). Err-methods share the `threshold` param, count-methods share `segments` (the same convention as `/api/steps`); conditions (flow, amp, freq, cycles, steps, lattice) are identical across runs, and results are **cached** (`COMPARE_CACHE`) so slider iterations are instant. Brute-force methods are runnable but slow. Runs that crash become `error` entries. **The per-method simulations run in PARALLEL on a per-request `ThreadPoolExecutor`** (≤ `SIM_WORKERS` = 6 workers — numpy releases the GIL for the vectorized LB passes, so the runs genuinely overlap); the sync path uses the same threaded runner, and a test asserts two runs land on distinct threads.
- **Background jobs + progress bar**: both fluid endpoints accept `async=1`, which starts the heavy work on the module-level `SIM_EXECUTOR` thread pool and returns `{"job": id}` immediately; the page then polls **`GET /api/fluid/progress?job=id`** (`{status: running|done|error, progress: 0..1, message, result|error}` — the result is delivered exactly once, then the job entry is removed; finished jobs are evicted beyond `SIM_JOBS_MAX`=16). `mfs.collect_frames` takes a `progress_cb(fraction)` (called ~every 1% of steps) that drives the progress updates; compare jobs aggregate the per-run fractions. The frontend (`fluid.js` `pollJob`) renders a slim progress bar under the header with the percentage and a message ("running 3/8 free-swim simulations ..."). The synchronous endpoints (no `async` param) are unchanged for tests/scripts.
- **Compare panel** (bottom of the fluid page): a checkbox list of all registry methods (brute-force off by default) + threshold/segments sliders + **Compare now**. Results render as (a) a summary table with the **best value per column highlighted** (max speed/thrust/efficiency/Strouhal/tail-amp, min power/cost/tracking-RMS), (b) **speed-vs-time and thrust-vs-time multi-series charts** (one colored line per run, palette by order), (c) **one clickable run card per method** (thumbnail of the final frame + speed/efficiency/joints) — clicking a card loads that run into the main viewer canvas (compare runs carry the same shape as `/api/fluid/simulate` responses: nx/ny/xs/ys/stride/rest/joint_pts/frames/frame_stride) for full playback with the frame scrubber; the fastest run is auto-loaded.
- `nx`/`ny` set the lattice size and are clamped to `100–800` × `80–480`. The page exposes them through a **low/medium/high/max resolution toggle** (`RESOLUTIONS = {low: 260×160, medium: 320×200, high: 400×240, max: 800×480}` in `fluid.js`, low = the original defaults, max = double of high on both axes); the fish body scales with `min(nx, ny)` (`fish_length = 0.55 · min`), so higher resolutions also lengthen the body in cells. **Ranges**: amp slider 0–40 cells, **wave cycles 0.4–10**, **steps 100–2400** (compare caps at 1600; backend clamps match), and **freq 0.0005–0.05 cycles/step set via a LOG-SCALE slider AND an exact-value text box** (`#freqVal`, kept in sync both ways — `sliderToFreq`/`freqToSlider` in fluid.js). The amp and freq controls are fully INDEPENDENT — dragging one never moves the other. The only coupling is the stability envelope: tail/head velocity `amp·2π·freq` must stay below ~0.19 cells/step or the moving bounce-back diverges on long runs, so the endpoint clamps to `amp·freq ≤ SimConfig.max_amp_freq` (0.03 — tightened from 0.05 because a 40-cell head sweep at the old boundary diverged within ~30 steps) — the backend clamp is the sole safety net, and the real (possibly clamped) values are shown in diagnostics.
- The page generates the joints and runs them through `midline_fluid_sim.Simulation` with the **joint configuration as the fish body rest shape** (`resample_polyline` turns the straight segments into a continuous node chain, preserved endpoints).
- Body scaling: joint positions are taken from frame 0 and ordered along the body via the nearest-neighbour chain (`trace_indices`), since CSV tracking data (`Fish_NN/Raw_Values_3D.csv`) has **unordered points** — raw generation order is scattered and would collapse the scaled body into a degenerate blob. The endpoint detects unordered data (generation order vs chain order agreement < 0.75) and then builds the body from the **smoothed traced chain** (`smooth_chain`, moving average) with the joints kept as markers (`body_kind: "traced"`); ordered `.xls` data keeps the actual joint segments as the body (`body_kind: "segments"`). Body spans 55% of the smaller lattice dimension, head at (nx/4, ny/2). Node count capped at 32 (`min(32, max(12, 8·(segments-1)))`).
- **No elasticity**: the body is always the articulated `RigidChainFish` — segments are exact rigid rods that only bend at the joints. In swim mode the joints are **actuated**: each segment gets a servo torque `k_act·(θ_target − θ)` toward the commanded traveling wave `θ_a = (s_a/L)·Θ_tail·sin(2πft − k·s_a)` (amplitude envelope linear along the body, Θ_tail solved in closed form so the tail lateral amplitude equals `amp`; the wave ramps in over 2 beat cycles and the fish **starts straight** — a robotic fish bends into the wave from a straight pose). The head segment is held straight by the orientation spring; the **head is dynamic** — the fluid force measured from the LB momentum exchange accelerates it (`F/mass`, damping, speed clip 0.05, periodic wrap as a safety net).
- **Force measurement** (`LBGrid.step` → `body_force`): Ladd's momentum exchange, summed **only over fluid→solid interface links** (interior solid-solid links carry no physical force and would inject garbage). Per-node forces are EMA-smoothed in time (`force_ema=0.04`, the body's inertia) and box-smoothed along the body chain; the net force accelerates the head (`force_scale`), while only a weak fraction (`torque_scale=0.02`) acts on the segments — the body is motor-driven, and the per-cell force noise would otherwise overwhelm the servo torques and whip the body around (this is what made early free-swim versions diverge). A **combined node-speed bound** scales the whole angular-velocity field (`Σ|ang_vel|·seg_len ≤ max_node_speed`), because coherent rotation of all segments swings the tail much faster than any per-segment clip bounds and destabilises the moving bounce-back. The simulator is **fully deterministic** (no RNG) — identical conditions give bit-identical metrics, so config comparisons are reproducible.
- **No walls**: the LB domain is fully periodic in both axes (the old no-slip bounce-back walls on the top/bottom rows are gone), so waves pass the edges instead of reflecting — like a fish in a much larger pool. The flow measurement window is the full y range (`ux[:, 40:nx-40]`) **with solid cells excluded** so the fish's own body does not pollute the flow controller; the x-edge sponge stays as a soft absorber.
- **Stability**: `SimConfig` in `midline_fluid_sim.py` holds the **tuned constants as the single default** (`mass=4, k_bend=5, k_orient=10, k_act=5, damp=0.03, damp_v=0.05, max_ang_vel=0.05, max_node_speed=0.18, max_amp_freq=0.03, max_head_speed=0.05, force_scale=3, force_ema=0.04, torque_scale=0.02`). The old CLI spring defaults rang violently on sharp joint kinks (node velocities hit the clip and the moving bounce-back injected huge momentum → NaN). The constants are tuned so the body **visibly articulates at the joints** (light inertia, little damping, strong head coupling). Don't hand-tune body params for generated-segment bodies — pass a `SimConfig` instead. Tethered stability regressions are covered by tests (amp=40 clamp case, flow convergence, no-wall wave pass-through).
- **LB performance** (~4× faster, 38 → 9 ms/step at 260×160): the distribution layout is **(9, ny, nx)** — the direction is the FIRST axis, so every per-direction operation works on a CONTIGUOUS plane (the old `(ny, nx, 9)` layout made `f[:, :, d]` a strided view that cost an extra copy per roll/op); the collision is IN-PLACE (`f *= 1−ω; f[d] += ω·feq + guo` computed plane-by-plane with cache-sized temporaries) and collide+stream share one per-direction loop; the d=0 roll (a wasted full-grid copy) is skipped; the fluid-force field is preallocated with the bulk-drag+sponge profile folded into one multiply; and `collect_frames` derives the flow speed from the velocity field it already computed (no second `lb.velocity()` call per recorded frame).
- The chain returns **per-frame joint positions** (`frames[i].joints = body[joint_idx]`, the articulation nodes of the deformed body), so the green markers sit exactly at the joints and move with the body.
- Response: velocity-magnitude field downsampled by `field_stride` (nx/48, min 4) + `frame_stride` (≤600 frames for single runs, ≤120 per run for compare) to keep JSON ~MBs; per-frame body polyline, measured flow speed, joints, rest shape, (swim: commanded wave), sim time. Frontend draws the field as a viridis-ish 3-stop color grid, body red, rest dashed, commanded wave cyan-dashed, joints/head markers, playback, plus a flow-vs-frame mini chart and diagnostics panel. Sim runs ~15 s for 600 steps on the 598-frame sturgeon CSVs — the progress bar shows the step fraction while it runs.
- **Playback**: `advancePlay(frame, n, loop, playDir)` in `helpers.js` is the single source of truth for the animation step (both `app.js` cards and `fluid.js` use it, and the node smoke unit-tests it): `loop` checked wraps end→start (always forward), unchecked rewinds (ping-pong bounce). The checkbox is per-card in the viewer (saved in sessions) and global on the fluid page.

### Step-through page (`/steps`, `web/steps.html` + `web/js/steps.js`)

- Compares growth methods by replaying their generation one joint at a time: `GET /api/steps?folder=&file=&methods=a,b,c&threshold=&segments=&max_steps=` runs each selected registry method with a `step_callback` recorder (`_record_steps`) that deep-copies the joint list after every step; snapshots are capped at `max_steps` (page default 400) by raising `_StopRecording` through the callback, which cleanly aborts every method (all of them propagate callback exceptions). Unknown ids fall back to the full registry; a method that crashes becomes an `error` entry without killing the request.
- The frontend fetches `/api/data` (same display payload as the main viewer) plus `/api/steps` in parallel, then renders one chart per method: the traced midline of the selected frame plus the joints at the shared step (positions re-located by row index onto the displayed frame, with stored frame-0 coords as fallback for padded frames). Charts freeze once their method finishes; runs that hit the cap are labelled "capped at N recorded steps".
- Controls: **Forward / Skip 5 / Back / Back 5** buttons plus a step slider (`gstate.maxSteps` = longest run; the shared step is clamped per chart), a frame slider, and method checkboxes (brute-force methods off by default). The page auto-runs after the file list loads.
- Keep `steps.js` on `getElementById` + `createElement` only (no `querySelector`) so the node smoke stub can assert on it; the smoke drives the step buttons through the stored `_listeners` and checks the counter text.
